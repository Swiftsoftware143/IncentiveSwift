Managing IncentiveSwift

This guide covers administrative configuration — managing tenants, plans, portfolio companies, integration provider keys, webhook security, and cross-app sync.

1 Admin Access

Admin Section

The Admin section appears in the sidebar for users with the agency_admin role. It expands as an accordion section showing:

  • 🏢 My Portfolio — Manage sister companies under your agency
  • 👥 Tenants — View all tenant accounts, assign plans, manage users
  • 💳 Plan Management — Create, edit, and delete subscription plans

Super Admin Role

Super admins have full access to all tenants and portfolio companies. They can:

  • View any tenant's data without impersonation
  • Assign or change plans for any tenant
  • Create and delete plans including feature sets
  • Impersonate tenants for troubleshooting (audited)

2 Tenants

Viewing All Tenants

The Tenants page lists all registered accounts in a searchable table. Each row shows:

  • Name — Tenant company or display name
  • Plan — Currently assigned plan name
  • Status — Active (●) or Suspended (●)
  • Users — Number of user accounts under this tenant
  • Created — Account creation date
  • Actions — View details, Assign Plan, Impersonate
GET /api/v1/admin/tenants          — List all tenants
GET /api/v1/admin/tenants/:id      — Tenant details

Assigning Plans

Click Assign Plan on any tenant to open a dropdown of all available plans. The plan change takes effect immediately — no confirmation from the tenant required.

PATCH /api/v1/admin/tenants/:id/plan   — Assign plan

Impersonating Tenants

Admins can log in as any tenant for troubleshooting. Click the 🔀 Impersonate button on the tenant detail view. The page reloads showing the tenant's dashboard with an orange banner. Click ← Back to Admin to exit impersonation.

Security: All impersonation actions are logged in the audit trail with admin identity and timestamp.

3 Plan Management

Creating Plans

From the Plan Management page, click + New Plan to create a subscription plan. Each plan has:

  • Name — Display name (e.g. "Professional", "Enterprise")
  • Price — Monthly and yearly pricing (USD)
  • Features — JSON object of feature flags and limits
  • Sort Order — Display order in dropdowns

Feature Flags

Plan features are defined as a JSON object. Each feature key maps to a boolean or numeric limit:

{
  "campaigns": true,           // Can create campaigns
  "iqs_surveys": true,         // Can use IQS surveys
  "integrations": 3,           // Max integration targets
  "provider_keys": true,       // Can add own API keys
  "widget": true,              // Popup widget access
  "analytics_export": true,    // CSV export from analytics
  "webhook_security": true,    // Domain allowlist + daily limits
  "embed": true,               // Campaign embedding
  "mobile_app": true,          // Mobile app access
  "credits": 1000              // Monthly OpenClaw credit allocation
}

Deleting Plans

Click the delete button on any plan. Tenants assigned to a deleted plan are moved to the default free plan. Active tenants are never left unassigned.

4 Portfolio Companies

Managing Sister Companies

The Portfolio section lets admin-level users manage multiple business entities under one account. Each portfolio company can have its own:

  • Separate campaign and survey data
  • Own integration provider keys (fallback chain)
  • Independent analytics and reporting
  • Custom branding and SEO settings

Adding Portfolio Companies

From Admin → My Portfolio, click + Add Company. Enter a name and slug. The company is created as a sub-entity under your account. You can switch between companies from the portfolio view.

GET  /api/v1/portfolio-companies      — List companies
POST /api/v1/portfolio-companies      — Create company

Cross-Company Copy

Share integration targets, templates, and campaigns across portfolio companies. Data isolated by company ID unless explicitly shared.

5 Integration Provider Keys

Provider Keys Overview

The Integration Hub relies on provider API keys stored in the Provider Keys section. These keys enable third-party service integration for campaign dispatch:

  • Marketing Boost — API key for email/SMS dispatch on wins and entries

Key Resolution Chain

When a campaign fires an integration, the system resolves provider keys in this priority order:

  1. Integration Target's own key — Key stored directly on the target record
  2. Portfolio company settings — Fallback to the portfolio company's provider keys
  3. User-level Provider Keys — Global keys stored in the Provider Keys table
Best practice: Store keys at the most specific level. Use user-level keys as a catch-all default.

Managing Keys

Navigate to Integrations → Provider Keys. Keys are encrypted at rest and masked in the UI. You can add, update, or delete keys. Key changes take effect immediately for subsequent integration dispatches.

6 Webhook Security

Admin Controls

Webhook security settings are configurable per integration target:

  • Allowed Domains — Restrict webhook dispatch to approved domains only. Enter comma-separated domains in the integration form.
  • Daily Limit — Set max webhook calls per day per integration target. Prevents runaway dispatch loops.
  • Delivery Log — Admins can view the delivery log showing every webhook attempt, status, and error message.

Enforcement

When a webhook is dispatched, the system checks the target domain against the allowlist. If not allowed, the dispatch is blocked and logged. If the daily limit is reached, further dispatches are blocked until the reset (24h from first dispatch).

Monitoring

Check the delivery log from the Integration Hub for blocked or failed dispatches. Failed dispatches include the HTTP response code and error message from the target server.

7 Credits & Billing

Plan-Based Credit System

IncentiveSwift uses a credit system for advanced features. Credits are allocated per plan and consumed by:

  • OpenClaw AI agent actions — Per-task credit consumption
  • Premium campaign types — Advanced campaign mechanics
  • Integration dispatches — Per-integration-fire credit

Admin Credit Management

Admins can view credit usage per tenant and adjust plan allocations. Credit balances are visible in the admin panel and in each tenant's Settings → Billing tab. Overages can be configured to block, warn, or auto-bill.

Free Tier vs Paid

The free tier provides access to basic campaign types and IQS surveys with limited features. Paid plans unlock premium campaign types, integrations, webhook security, analytics export, and increased credit allocations.

GET /api/v1/billing/credits — View current credit balance
GET /api/v1/admin/credits   — View all tenant credits (admin)

8 ⚖️ Loyalty Program Management

Credit Rate Management

Admins can view and update credit rates for each tenant. The credit rate determines how many credits a customer earns per $1 spent during purchase verification. Rates can range from 1 (minimum) to 1000 (maximum) credits per dollar, with a default of 10.

To update a tenant's credit rate:

PATCH /api/v1/admin/tenants/:id/credits-rate
{
  "credits_rate": 15
}

The auth guard ensures that a company_admin can only change the credit rate for their own tenant. Agency admins can change rates for any tenant under their portfolio. Super admins have unrestricted access.

Tip: Rate changes take effect immediately for future purchase verifications. Historical transactions are not recalculated.

Purchase PIN Administration

Purchase PINs are auto-generated sequentially (format Z100, Z101, etc.) when a tenant signs up. They are read-only in the tenant's UI — tenants can view but not modify their PIN.

Admins can view any tenant's PIN:

GET /api/v1/admin/tenants/:id/purchase-pin

If a PIN reset is required (e.g., compromised PIN), this is a manual database operation performed by a super admin. Every reset is logged in the audit trail with the admin identity, timestamp, old PIN, and new PIN.

Security: PIN resets should be rare. Require written authorization from the tenant's company admin before proceeding. Verify identity through a secondary channel (phone call or verified email).

Offer Oversight

Admins can view all offers across all tenants from the admin panel. This provides visibility into what discounts tenants are offering and helps maintain quality control.

Key monitoring responsibilities:

  • Check for negative caps — The cap_dollars field must always be greater than 0. Negative or zero caps can break the discount calculation.
  • Watch for >100% discount — The discount_percent field is validated server-side to 1–100, but review extreme values (90%+) for business appropriateness.
  • Deactivate problematic offers — If an offer violates policy or appears abusive, set it to Inactive. This prevents it from appearing during purchase verification while preserving the offer record.
Note: The server enforces that discount_percent must be between 1 and 100 and cap_dollars must be greater than 0. These validations prevent many common issues at the API level.

Fraud Monitoring

Admin-level fraud monitoring is essential for maintaining the integrity of the loyalty program. Common patterns to watch for:

  • Same PIN at multiple locations simultaneously — A Purchase PIN used at different merchant locations within seconds or minutes may indicate a shared or compromised PIN.
  • Self-referral loops — A customer creating multiple accounts and referring themselves to earn bonus credits repeatedly. Watch for referral patterns where multiple accounts share the same device, IP, or contact info.
  • Inflated purchase amounts — Unusually high purchase amounts compared to typical transactions at a merchant. This could be an attempt to earn excessive credits.

All admin actions are logged. Every view of a tenant's PIN, every credit rate change, every impersonation, and every offer status change is recorded in the audit trail with admin identity, timestamp, and action details.

Important: If you suspect fraud, gather evidence (screenshots, timestamps, affected account IDs) before taking action. Contact the tenant's company admin to verify legitimate use before locking accounts.

Voucher & Redemption Auditing

Admins can review voucher issuance and claim history across all tenants. The audit log shows:

  • Which customer received which voucher
  • When the voucher was issued and its expiration date
  • Whether the voucher was claimed, and the claim code returned
  • Any voucher redemptions against actual purchases

If a voucher has expired before the customer could use it, an admin can re-issue it with a new expiration date. This requires admin approval and is logged in the audit trail. Re-issued vouchers get a new voucher ID linked to the original in the audit record.

Best practice: Set voucher expiration to a reasonable window (30–90 days) to encourage timely redemption while giving customers adequate time to use their rewards.
