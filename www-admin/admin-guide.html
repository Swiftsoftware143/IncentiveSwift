Managing IncentiveSwift

This guide covers administrative configuration — managing tenants, plans, portfolio companies, integration provider keys, webhook security, and cross-app sync.

1 Admin Access

Admin Section

The Admin section appears in the sidebar for users with the agency_admin role. It expands as an accordion section showing:

  • 🏢 My Portfolio — Manage sister companies under your agency
  • 👥 Tenants — View all tenant accounts, assign plans, manage users
  • 💳 Plan Management — Create, edit, and delete subscription plans

Super Admin Role

Super admins have full access to all tenants and portfolio companies. They can:

  • View any tenant's data without impersonation
  • Assign or change plans for any tenant
  • Create and delete plans including feature sets
  • Impersonate tenants for troubleshooting (audited)

2 Tenants

Viewing All Tenants

The Tenants page lists all registered accounts in a searchable table. Each row shows:

  • Name — Tenant company or display name
  • Plan — Currently assigned plan name
  • Status — Active (●) or Suspended (●)
  • Users — Number of user accounts under this tenant
  • Created — Account creation date
  • Actions — View details (GET /admin/tenants/:id), read/write the credits rate, read a purchase PIN, adjust credits, and delete the tenant
GET /api/v1/admin/tenants          — List all tenants
GET /api/v1/admin/tenants/:id      — Tenant details

Assigning Plans

Plan assignment is an operator control in the console's Plans section — Assign plan to account. It takes the target plan id and the account id and applies the change immediately; no confirmation from the tenant is required. There is no per-tenant "Assign Plan" button on the Tenants table.

POST /api/v1/admin/plans/assign   — Assign plan (fields: plan_id, account_id)

Impersonating Tenants

Admins can impersonate a tenant for troubleshooting. In the console, the Portfolio Companies table carries a 🔑 Impersonate button per row, and the Support impersonation section has Impersonate user (POST /api/v1/admin/impersonate) and Stop impersonation (POST /api/v1/admin/stop-impersonation).

Security: All impersonation actions are logged in the audit trail with admin identity and timestamp.

3 Plan Management

Two separate surfaces

The console keeps the marketing catalogue and entitlements apart, and so should you:

  • 💳 Plans — the subscription rows the marketing site and checkout read. The panel edits only Name, Monthly price and Yearly price. It has no feature fields; whatever a customer is allowed to do is not set here.
  • 🥇 Plan Tiers — the Features & Plans panel. The entitlement model (plan_tiers → tier_features → features), and the only thing every runtime gate reads.

Plan Tiers — reading the screen

  • Left column — one card per tier: name, slug, $<price>/mo, an Active/Off badge, and Edit tier (name, slug, monthly/annual price, active, max_campaigns, max_entries_per_month).
  • Right column — <Tier> — Features with that tier's Campaigns / Entries/month / Annual numbers, then one card per feature category, in the order mechanic, delivery, branding, surface, module, loyalty, limits, billing.
  • One row per registry key — a checkbox (tier_features.enabled) with a green ADDED or red REMOVED badge, the bold label, the monospace key, and a number box (tier_features.limit_value).
  • Every registry key is listed on every tier — a key the tier has no row for still renders (unticked, REMOVED). Nothing is hidden from you.

Plan Tiers — saving

  • Ticking or unticking the checkbox saves immediately and the list reloads: "Changes hit the live runtime gate immediately."
  • The number box saves when you click away from it, and it sends the checkbox state as it is right then. On a key that has no row yet: tick the box first, then type the number — typing a number into an unticked row saves enabled = false alongside that number.

limit_value means the same thing in every reader:

Which keys the runtime actually reads

The panel lists a key whether or not any code reads it, so a full grid is not the same thing as a fully enforced product:

  • all_mechanics and each mechanic_<type> — 402 at play time.

  • custom_domains — the plan verdict on GET /api/v1/admin/plans/:id/domains.

Deleting Plans

Click the delete button on any plan. Tenants assigned to a deleted plan are moved to the default free plan. Active tenants are never left unassigned.

4 Portfolio Companies

Managing Sister Companies

The Portfolio section lets admin-level users manage multiple business entities under one account. Each portfolio company can have its own:

  • Separate campaign and survey data
  • Own integration provider keys (fallback chain)
  • Independent analytics and reporting
  • Custom branding and SEO settings

Adding Portfolio Companies

From Admin → My Portfolio, click + Add Company. Enter a name and slug. The company is created as a sub-entity under your account. You can switch between companies from the portfolio view.

GET  /api/v1/portfolio-companies      — List companies
POST /api/v1/portfolio-companies      — Create company

Cross-Company Copy

Share integration targets, templates, and campaigns across portfolio companies. Data isolated by company ID unless explicitly shared.

5 Integration Provider Keys

Provider Keys Overview

The Integration Hub relies on provider API keys stored in the Provider Keys section. These keys enable third-party service integration for campaign dispatch:

  • Marketing Boost — API key for email/SMS dispatch on wins and entries

Key Resolution Chain

When a campaign fires an integration, the system resolves provider keys in this priority order:

  1. Integration Target's own key — Key stored directly on the target record
  2. Portfolio company settings — Fallback to the portfolio company's provider keys
  3. User-level Provider Keys — Global keys stored in the Provider Keys table
Best practice: Store keys at the most specific level. Use user-level keys as a catch-all default.

Managing Keys

Navigate to Integrations → Provider Keys. Keys are encrypted at rest and masked in the UI. You can add, update, or delete keys. Key changes take effect immediately for subsequent integration dispatches. A stored endpoint must be a public destination: a base URL that resolves to a private, loopback or link-local address is refused when it is saved and is never contacted by a dispatch. The platform's own CoreSwift bridge is the one exception — it is the preset endpoint those accounts already use.

Chat Funnel AI replies

The Chat Funnel mechanic answers a visitor's typed message with an LLM when the account has connected an LLM provider key (resolved per account, DeepSeek preferred, OpenAI fallback), and otherwise replies with the campaign's scripted chat_flow. Both providers are in the catalogue and are connected from the same Provider Keys screen; their public vendor endpoints are the default, so no base URL is required. A tenant-supplied base URL follows the same public-destination rule as every other provider — a private relay needs a platform preset for that provider, which the platform seats, not the tenant.

6 Webhook Security

Admin Controls

Webhook security settings are configurable per integration target:

  • Allowed Domains — Restrict webhook dispatch to approved domains only. Enter comma-separated domains in the integration form. An empty list allows any public domain; private, loopback and link-local addresses are refused for every target.
  • Daily Limit — Set max webhook dispatches per day per integration target. Prevents runaway dispatch loops. The window is the UTC day, so the count resets at midnight UTC.
  • Delivery Log — Admins can view the delivery log showing each dispatch attempt to an integration target, its status and its error message. A dispatch refused by a security check is never sent, so it appears in the platform log rather than the delivery log.

Enforcement

When a webhook is dispatched, the destination host is resolved and refused if it points at a private, loopback or link-local address, then the target's domain is checked against its allowlist. If it is not allowed, the dispatch is refused before the request is made and the reason is logged. If the daily limit is reached, further dispatches are refused until midnight UTC. Redirects are not followed. The production delivery paths apply the same checks as the Test Webhook panel.

Monitoring

Check the delivery log from the Integration Hub for blocked or failed dispatches. Failed dispatches include the HTTP response code and error message from the target server.

7 Credits & Billing

Plan-Based Credit System

Credits are held per account (accounts.credits_balance). A plan tier can grant a monthly allowance and an overdraft entitlement (tier_features → credits_monthly / credits_overdraft, set per tier on the Plan Tiers tab — -1 = unlimited, 0 or no limit assigned = none included); with no limit assigned, the allowance reads 0 (none included). Credits are earned, not burned: purchase verification credits the account at that tenant's own credit rate ($1 = 10 credits by default), and the loyalty win and offer flows move them. No platform action deducts credits today.

Admin Credit Management

Admins can view every account's credit state in one place — the Operator Console's Credits (all accounts) panel lists each account with its plan, balance, lifetime used, ZC pool and credit rate. Use Adjust credits to change one account's balance, and the credits-rate call under Loyalty Program Management to change what that tenant earns per dollar. There is no overage policy to configure: an exhausted allowance is neither blocked, warned nor billed.

Free Tier vs Paid

The free tier provides access to basic campaign types and IQS surveys with limited features. Paid plans unlock premium campaign types, integrations, webhook security and analytics export.

GET  /api/v1/credits/balance  — View current credit balance
GET  /api/v1/admin/credits    — View all tenant credits (admin)

8 ⚖️ Loyalty Program Management

Credit Rate Management

Admins can view and update credit rates for each tenant. The credit rate determines how many credits a customer earns per $1 spent during purchase verification. Rates can range from 1 (minimum) to 1000 (maximum) credits per dollar, with a default of 10.

To update a tenant's credit rate:

PATCH /api/v1/admin/tenants/:id/credits-rate
{
  "credits_rate": 15
}

The auth guard ensures that a company_admin can only change the credit rate for their own tenant. Agency admins can change rates for any tenant under their portfolio. Super admins have unrestricted access.

Tip: Rate changes take effect immediately for future purchase verifications. Historical transactions are not recalculated.

Purchase PIN Administration

Purchase PINs are auto-generated sequentially (format Z100, Z101, etc.) when a tenant signs up. They are read-only in the tenant's UI — tenants can view but not modify their PIN.

Admins can view any tenant's PIN:

GET /api/v1/admin/tenants/:id/purchase-pin

If a PIN reset is required (e.g., compromised PIN), this is a manual database operation performed by a super admin. Every reset is logged in the audit trail with the admin identity, timestamp, old PIN, and new PIN.

Security: PIN resets should be rare. Require written authorization from the tenant's company admin before proceeding. Verify identity through a secondary channel (phone call or verified email).

Offer Oversight

Admins can view all offers across all tenants from the admin panel. This provides visibility into what discounts tenants are offering and helps maintain quality control.

Key monitoring responsibilities:

  • Check for negative caps — The cap_dollars field must always be greater than 0. Negative or zero caps can break the discount calculation.
  • Watch for >100% discount — The discount_percent field is validated server-side to 1–100, but review extreme values (90%+) for business appropriateness.
  • Deactivate problematic offers — If an offer violates policy or appears abusive, set it to Inactive. This prevents it from appearing during purchase verification while preserving the offer record.
Note: The server enforces that discount_percent must be between 1 and 100 and cap_dollars must be greater than 0. These validations prevent many common issues at the API level.

Fraud Monitoring

Admin-level fraud monitoring is essential for maintaining the integrity of the loyalty program. Common patterns to watch for:

  • Same PIN at multiple locations simultaneously — A Purchase PIN used at different merchant locations within seconds or minutes may indicate a shared or compromised PIN.
  • Self-referral loops — A customer creating multiple accounts and referring themselves to earn bonus credits repeatedly. Watch for referral patterns where multiple accounts share the same device, IP, or contact info.
  • Inflated purchase amounts — Unusually high purchase amounts compared to typical transactions at a merchant. This could be an attempt to earn excessive credits.

All admin actions are logged. Every view of a tenant's PIN, every credit rate change, every impersonation, and every offer status change is recorded in the audit trail with admin identity, timestamp, and action details.

Important: If you suspect fraud, gather evidence (screenshots, timestamps, affected account IDs) before taking action. Contact the tenant's company admin to verify legitimate use before locking accounts.

The float rule — the three conditions the guard enforces

IncentiveSwift’s loyalty programme has its own float: the businesses fund the rewards their members earn, and the platform holds a redemption that would leave the float short. The rule is three independent conditions, and a redemption is held if any of them fails. The console shows all three with the numbers that decided each one, and the hold record names the condition that was short.

  • Coverage — the float covers at least float_coverage_pct% of the value of the points members are holding. Default 100. Accounting view: never redeem points nobody funded.
  • Burn — the float holds at least float_burn_months months of trailing-30-day redemptions (measured from point_redemption_log, the same rows the programme actually paid). Default 1. Operational view: a fully covered programme can still run dry when several members redeem at once.
  • Floor — the float never falls below minimum_float, the safety balance. A new programme has near-zero liability and near-zero burn, so the floor is what stops an empty programme paying out.

On breach the programme holds the payment to the business for that redemption: the customer has already been given their reward at the counter, nothing is confiscated, and the held payment waits in the Ledger tab until the float is back above all three conditions. The hold record names the condition that was short.

Where the knobs live

Admin console → Ledger tab → Change the rule. It prompts for the breach behaviour, the floor (safety balance), the coverage % and the burn months. The same three thresholds are readable on Settings (Min Treasury Float / Float Coverage / Float Burn) and through GET /api/v1/admin/treasury/state, GET /api/v1/admin/clearinghouse/config and PUT /api/v1/admin/treasury/rule (fields minimum_float, float_coverage_pct, float_burn_months). A zero or negative coverage/burn is refused with 400 rather than saved and ignored — a programme protecting 0% is not protected at all, and a malformed stored value falls back to the safe default (100% / 1 month).

Best-practice values

  • Coverage 100%. Lower it only when deliberately extending credit to a business, and record the decision.
  • Burn 1 month, raised toward 2–3 for seasonal programmes (holiday/event-driven redemption).
  • Floor: a real number for the smallest business onboarded.
  • Review after every large campaign — coverage self-corrects as points are redeemed; burn does not, because a campaign raises redemptions immediately.

What to tell a business

They fund before launch and top up before growing; a held payment is not a loss (the customer keeps their reward; the business is reimbursed after topping up); and they will always be told which condition is short and by how much. The businesses’ own guide (User Guide → Loyalty Program → “How the programme stays funded”) and the generated rules page (GET /api/v1/treasury/rules) carry the same conditions, written from the settings actually in force.

Tip: The published rules are GENERATED from the rule in force, so a business can never read a rule the software is not applying — change a knob and the sentence they read changes with it.

9 ⏳ Points Expiry

What the Sweep Does

POST /api/v1/admin/treasury/expire-points expires loyalty points that have fallen outside their program's expiry window. It works by recomputing each member's unexpired balance from the point ledgers and setting the balance to that number — it does not decrement.

unexpired_balance = GREATEST(0, unexpired_earned - redeemed)

Because the inputs are the (immutable) ledgers, a second run computes the same number, sees the stored balance already matches, and writes nothing. Re-running the sweep is a no-op, so it is safe to call on a schedule — or twice by mistake.

The sweep only ever lowers a balance. Only members with a positive balance are considered, and a member whose ledger total is already at or above their stored balance is left untouched.

Running It

From the admin app: open the Operator Console (🛠, admin-only) and find the panel 8 · Treasury, clearinghouse & site ops. Click Expire points now. That control calls the endpoint with your session token and prints the raw JSON response inline with an OK / ERROR flag.

POST /api/v1/admin/treasury/expire-points

The endpoint takes no parameters and no request body, so there is nothing to fill in before running it.

Expiry Window (Per Program)

The cutoff is resolved per program, not globally, from loyalty_programs.points_expire_days. A program with no value set falls back to 365 days. Each member is cut off using their own program's window.

To shorten or extend a program's window, set points_expire_days on that program row. Nothing moves until the sweep runs — the window only affects the next expiry run, not existing balances.

Which Ledgers Count

DirectionLedger / ColumnTimestamp Used
Earnloyalty_checkins.points_awardedchecked_in_at
Earnloyalty_online_actions.points_earnedcreated_at
Earnpoint_issuance_log.points_issuedcreated_at
Spendpoint_redemption_log.points_redeemed— (all-time total, not windowed)

Redemptions are treated as consuming the oldest points first (FIFO) — the points a member still holds are their newest. That is why the full redemption total is subtracted from the unexpired earn total rather than allocated against individual earn rows.

loyalty_activity is deliberately excluded: it mirrors the check-in rows, so counting it would double-count every check-in.

All three earn ledgers matter. Because the balance is set to the recomputed figure, a ledger left out of the sum would not merely go un-expired — those points would be deleted. There are exactly three ledgers that credit points_balance.

Treasury liability is reduced once, after every member has been processed — never inside the per-member loop — and it is floored at zero.

Auditing and Reversing a Run

Every run writes exactly one row to point_expiry_audit, and it is written before any balance is changed. The row carries the previous balance of every member the run intended to change, so a run is inspectable and reversible even if it dies halfway through.

ColumnMeaning
idRun id — the audit_id returned by the API.
run_at / completed_atWhen the run started, and when it finished reconciling.
statuspending while planned, then applied if any balance changed, or noop if none did.
default_expire_daysFallback window used for the run (365).
members_affected, total_points_expired, treasury_liability_reductionRun totals, matching the API response.
detailsJSONB array, one entry per member. Planned before the write: member_id, program_id, expire_days, cutoff, previous_balance, new_balance, expired_points, unexpired_earned, expired_earned, redeemed. Once the run completes it is rewritten with the outcome per member — applied (carrying previous_balance and new_balance) or skipped_conflict.

To reverse a run: read details for the audit_id, set each listed member's points_balance back to its previous_balance, and add that run's treasury_liability_reduction back onto point_treasury.outstanding_liability. Because the sweep only ever sets a balance from the ledgers, the next run simply re-derives the current state.

Before you reverse: check the status first. A noop row changed nothing and needs no reversal.
Concurrent awards are not clobbered. Each member's write is guarded on the balance the plan observed; if a member's balance moved in between, that member is skipped and counted in skipped_conflicts, and the next run picks them up.

10 🧩 Grouped Form Sections

What Sections Are

Campaigns of Mechanic Type Long-Form Qualifier can group their questions into titled sections (for example About you → Your business → Your goals). Sections live in campaigns.config.sections:

[
  { "title": "About you",     "questions": ["full_name", "role"] },
  { "title": "Your business", "questions": ["company", "monthly_revenue"] }
]

This is an ordering-only overlay. It decides the grouping and presentation order of the questions on the public form, and nothing else.

Sections cannot change qualification. Scoring, outcomes, tags, redirects and the outcome webhook all keep reading config.rules exactly as they did before sections existed. Grouping a question differently, or not at all, cannot change who passes.

Editing Sections

Open a Long-Form Qualifier campaign in the campaign editor. A 🧩 Sections block appears under the Config (JSON) field, annotated presentation order only — scoring, outcomes, tags, redirects and the webhook are unchanged.

  • + Add section — appends a new section with an editable title and a ✕ remove button.
  • Question checkboxes — the list is built from the question keys already present in config.rules. Tick a key to place it in that section, untick to take it out.
  • If rules is still empty the block says so: No question keys in config.rules yet — add rules above, then group them here.

campaigns.config is JSONB and is replaced wholesale on save, so the editor merges sections into the config object alongside rules and outcomes. Saving sections never wipes the rules or outcomes.

Where It Renders

The public form page (https://incentiveswift.com/long-form-qualifier.html?slug=<campaign>) consumes form_sections from GET /api/v1/play/<slug> and prints one heading per non-empty section, with that section's questions beneath it. When the key is absent the page falls back to the flat config.rules order.

Campaign & Survey Platform Administration

Tag to free account

This is the switch that makes the affiliate tag system actually create accounts. When an affiliate tags a lead with one of this app's tags — for example "IncentiveSwift — Free" — IncentiveSwift is told to create a free account for that lead, using the same name and email the lead was captured with in FunnelSwift. IncentiveSwift then emails the new user their login details automatically, so the lead can sign in and upgrade here whenever they are ready.

Where the switch is

In this console, in the left sidebar under Provisioning (the tag icon). That screen shows the current state, flips the switch and picks the entry tier for a minted account. The setting is stored as provision_from_tags_enabled.

What happens when it is ON

  • A tagged lead gets a real account here on the free plan - not just a contact record
  • The new user is emailed their login details by IncentiveSwift
  • Tagging the same lead twice does not create a duplicate account - the second attempt is recognised by email and ignored

What happens when it is OFF

The tagged lead is still recorded here as a contact, so nothing is lost, but no account is created and no login email is sent. Use this if you want to review leads before accounts exist for them.

Why it works this way

FunnelSwift is the hub where affiliates and leads live. Tagging is how a lead is routed to the software they are interested in. The account is created here, in the destination app, so the lead signs in at the app they actually want - and upgrades on this app's own plans and pricing.
